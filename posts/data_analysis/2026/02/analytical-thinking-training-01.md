# 1. 문제 정의

> 우리는 더 나은 '의사결정'을 돕기 위해 데이터 분석을 한다.  
> 이 다음엔 무엇을 해야 하는가? 라는 질문에 답해야 한다.

## 데이터 분석의 두 가지 상황
### 1. 데이터 셋만 있을 때
> 이 데이터셋으로 어떤 의사결정에 도움을 줄 수 있을까?

의사결정을 돕는 **가치있는 질문**을 찾는 순서가 필요하다.

❔**질문과정**
```text
1. 보고 대상이 누구인가 ➡ 데이터
2. 보고 대상은 이 데이터를 통해 어떤 의사결정이 필요할까 (모호하다면 데이터 제공처의 비즈니모델이나 목표를 생각해본다) ➡ 지표/모델
3. 어떤 결과물이 이 의사결정을 가장 잘 도울 수 있을까 ➡ 산출물
	- 모델링?
	- 대시보드?
	- 인사이트 보고서?
```

### 2. 문제가 주어졌을 때
> 이 모호한 문제 뒤에 숨어있는 진짜 의사결정 니즈가 무엇일까?

이 현상 뒤에 숨겨진 의사결정을 찾아야 한다.

❔**질문과정**
```text
1. 요청사항을 꼼꼼히 파악 한다 ➡ 문제
2. 데이터 분석을 통해 어떤 의사결정이 필요한지 질문한다 ➡ 지표/모델
3. 의사결정에 맞는 결과물에 대해 합의한다 ➡ 산출물
```

> 요청자의 의사결정에 꼭 필요한 '원인분석'을 통해 의미있는 분석을 한다.

### 💡Tips
### Devil's Advocate (악마의 변호사)
➡ 분석/논리의 모든 단계를 **스스로가 가장 신랄하게 공격하는 선의의 비판자**가 되는 것
왜 이 과정일 필요한가?

- 내 논리의 치명적인 허점을 미리 찾기 위해
- 그에 대한 방어 로직을 만들기 위해
- 내 분석이 견고하고, 의미 있도록 만들기 위해

```
1. 이 데이터는 믿을 수 있나?
	- 나와 팀이 서로 다른 것을 정의하고 있지는 않는가?
3. 이 문제는 풀 가치가 있나?
	- 나만 궁금한거 아니야?
	- 통계적으로 유의미하다고 해도 비즈니스적 가치가 있을까?
4. 이 결론은 진짜인가?
	- 운이 좋았던 건 아닐까?
	- 내 분석 덕분이 아니라 다른 요인 때문은 아닐까?
```
# 2. 가설을 세우고 테스트 가능한 형태로 변형하기

## 좋은 가설은?
➡ 검증이 가능하고 행동으로 이어져야 한다.

## 좋은 가설의 3가지 조건: RSA
### Relevant(비즈니스 목표와 관련이 있는가)
- 우리 회사/팀의 핵심 목표와 맞는가.

### Specific(구체적인가)
- 누가, 무엇을, 어떻게 했는지 명확하고 측정 가능해야 한다.

### Actinable(실행 가능한가)
- 세운 가설이 맞거나 맞지 않은 경우 다음 해야 할 행동이 명확해야 한다.

```
💡Relevant 가 가장 중요한 이유
가설에 검증 성공 하더라도 비즈니스 임팩트가 더 중요하다.
```

## 가설 검증 방법
### A/B 테스트
- 사용자를 무작위하게 A/B 그룹으로 나눠서 편견없이 인과관계를 증명한다.

### A/B 테스트가 불가능한 상황
1. 물리적, 윤리적으로 불가능
- i.e "흡연이 건강에 미치는 영향"
- i.e "심각한 버그가 이탈율에 미치는 영향" (일부러 버그를 노출시킬 수 없음)

2. 이미 '원해서 선택' 한 경우 (Self-Selection Bias)
- 유료 멤버십을 원해서 선택한 사용자는 원래 구매 의향도가 높고 서비스 충성도가 높음

### Alternative (인과추론)
이미 관찰된 데이터만으로 공정한 비교를 할 수 있도록 비교하는 기법
> A/B 테스트가 불가능한 가설에 대해 A/B 테스트를 했다면 어떤 결과가 나왔을까?

```
💡EDA는 답을 찾는것이 아니라 새로운 질문을 찾아가는 과정
```
# 3. 문제의 원인을 찾는 방법
> 분석가는 '과정/원인'을 본다.

## 원인 분석의 4단계
1. **Metric Decomposition:** '결과'를 '과정' 지표로 쪼갠다.
2. **Localization:** "누구? 어디서? 언제?" 렌즈로 현상을 관찰한다.
   1. **Segment(who?):** 어떤 사람에게 문제가 생겼나? (i.e. ios/android, 신규/재방문, 20/40대)
   2. **Funnel(where?):** 어느 단계에서 이탈했나? (i.e. 방문 > 장바구니 > 결제 > 완료)
   3. **Cohort Analysis(when/who?) - 공통된 경험을 한 집단:** 언제 가입/방문한 집단에게 문제가 생겼나? (i.e. 10월 가입자 vs 11월 가입자)
3. **Hypothesize & Test:** 가설을 세우고 실제로 유의미한지 통계로 확인한다.
4. **Action:** 다음 단계를 제안한다.

# 4. 결과를 설명하는 방법
## 스토리텔링
> 스토리텔링은 데이터를 '단순 보고서'가 아닌 '사람을 움직이는 도구'로 바꾸는 기술

## 결론부터 말한다
> 그래서 우리는 무엇을 해야한다.

구체적으로 어떤 Action 을 취해야 하는지 먼제 이야기한다.

```text
💡 결론 ➡ 핵심 근거 ➡ 분석 증명
```
### 1. 결론
- 어떤 구체적인 Action 을 취해야 하는지
### 2. 핵심 근거
- 전문 용어를 비즈니스 용어로 전환
- 데이터 분석을 모르는 사람들이 들어도 이해 가능한 방식
### 3. 분석 증명
- 결론과 핵심 근거를 이미 청중이 들었기 때문에 모델과 분석 과정을 결론을 뒷받침하는 근거로 받아드릴 준비가 되어있음
- 분석 과정을 설명

💡 **TOP(Time Person Occasion):** '누구'에게 보고하는가?   
- 청중 대상과 관심사에 맞는 결과와 용어로 실행 방식을 제안한다.
